Estilo de arquitectura y patrones
Qué estilo y qué patrones usamos hoy y por qué. Lo decidido cita su ID de Notion; lo propuesto aún no está registrado.
Estilo de arquitectura
Tres capas (D1)
El controlador mueve el brazo, el edge
orquesta cada toma y la nube sirve el
video. Cada capa trabaja en su propia
escala de tiempo.
Edge offline-first (D17, C3)
Todo el camino de la toma es local. Los
resultados salen por una cola cuando hay
internet: guardar y reenviar.
Un solo proyecto en la nube (D27)
La web y la API van juntas en Astro. Sin
microservicios ni broker de mensajes.
Consultas periódicas, sin tiempo real
(D14).
Orquestación, no eventos
session/ le dice a la cámara y al robot
qué hacer, paso a paso. Nada reacciona a
eventos sueltos.

Patrones de aplicación y de datos
Aplicación
Interfaz del operador y Studio: páginas HTML planas servidas por el edge, con
JavaScript solo donde hace falta (regla 6).
Admin web: renderizado en el servidor con Astro y componentes interactivos puntuales.
Página del invitado: casi estática y cacheable.
Sincronización en un sentido por vez: el edge baja el catálogo antes del evento y sube
los resultados después.
Subida idempotente: el id lo genera el edge y la web hace upsert.
Datos
Relacional: Postgres en Supabase (D28), con la clave generada del lado del edge.
Archivo aparte, referencia en la base: el video vive en R2 y la base guarda solo
video_bucket_key (claim check).
Versiones inmutables de las rutas: editar crea otra fila, y cada toma apunta a la
suya.
Ciclo de vida: retención configurable y anonimización con limpieza diaria (D30,
D31).
Consistencia eventual: una toma es del edge hasta que sube, y de la nube después.
Local en el edge: una carpeta por toma y la cola persistente. El almacenamiento de la
cola no está decidido; propongo SQLite.
Lo que no usamos, a propósito
Microservicios, event sourcing, CQRS, DDD, un broker de mensajes, una capa de repositorios sobre Supabase y una capa de caché. No hacen falta para este tamaño y cada una añadiría
piezas que mantener.
